# FitProof 移动端布局与视频内容路由设计

日期：2026-08-09

## 背景

FitProof 在不同手机浏览器上的首页高度表现不一致：部分设备可看到完整页面，部分设备必须向下滚动才能看到分析按钮。现有首页混用了 `100vh`、`100dvh` 和固定底部导航，但正文只按 54px 预留空间，没有把动态浏览器工具栏与 `safe-area-inset-bottom` 统一纳入布局计算。

单视频分析链路还缺少健康领域准入判断。视频完成转写后，无论内容是否与健康相关，都会进入“拆出 3–5 条健康主张”的提示词，模型因而可能对足球、旅游或普通生活视频强行生成健康解读。

## 目标

1. 在常见手机浏览器中消除横向溢出和底部导航遮挡。
2. 在普通手机高度下让输入框、上传入口和主分析按钮首屏可见。
3. 在矮屏、横屏和字体放大场景中允许自然纵向滚动，不通过过度缩小文字强塞一屏。
4. 在主张提取前识别视频是否属于 FitProof 的健康核验范围。
5. 接受明确健康主张，以及围绕健康目标展示的可模仿行为方案；拒绝仅有健康场景或完全无关的内容。
6. 不向被拒绝内容提供“仍然分析”入口。

## 非目标

- 不重新设计结果页、知识库或个人页的视觉风格。
- 不扩展 FitProof 到娱乐、体育赛事、旅游等通用视频分析。
- 不依赖关键词直接拒绝边界内容。
- 不保证所有内容在所有设备、所有字体倍率下严格一屏展示。

## 方案概览

采用“高度响应式首页 + 复用式两级内容路由”。

- 首页使用真实可用视口高度和统一的底部安全区变量，根据可用高度逐级减少留白。
- 第一级使用已有媒体元数据做零额外模型调用的保守预筛，只拒绝高置信度无关内容；缺少可靠信息时必须返回不确定并继续转写。
- 第二级把现有关键帧闸门升级为内容路由器。它继续决定是否需要画面，同时返回领域类别、继续/停止决定、理由和原文依据。
- 需要画面才能判断的内容先完成关键帧解读，再做最终领域决定。

## 移动端布局设计

### 统一视口与底栏空间

页面外壳以 `100dvh` 表示当前实际可见高度，并提供旧浏览器可接受的自然文档流回退。正文只由一个外壳负责高度，不在 `InputPage` 内继续使用 `min-h-screen` 或 `calc(100vh - ...)`。

定义共享底部空间：

```css
--bottom-nav-height: 54px;
--bottom-safe-area: env(safe-area-inset-bottom, 0px);
--bottom-app-inset: calc(var(--bottom-nav-height) + var(--bottom-safe-area));
```

固定导航和正文底部留白都使用同一组变量，避免视觉高度与预留高度不一致。根布局声明支持 edge-to-edge 时，仍必须把可操作控件放在安全区内。

### 高度密度分级

- 高屏（可用高度至少 780px）：保留现有较舒展的品牌卡片、间距和内边距。
- 普通屏（640–779px）：减少页面上下留白、卡片内边距和区块间距；两个操作按钮并排，主分析按钮保持首屏可见。
- 矮屏（低于 640px）：品牌区改为紧凑排布，继续保持正文可读字号和至少 44px 的主要点击区域；允许少量纵向滚动。

宽度仍采用移动优先的单列回流。320 CSS px 宽度下不得出现页面级横向滚动。系统字体放大导致内容变高时，页面必须自然延长，不能截断文字或隐藏操作。

### 验收行为

- 320×568：可纵向滚动；无横向溢出、底栏遮挡或不可访问控件。
- 360×640：默认字体下输入框、上传入口和主分析按钮首屏可见。
- 390×844、430×932：使用舒展布局，无多余强制滚动。
- 横屏：允许滚动；左右和底部安全区内的控件完整可用。
- 移动浏览器地址栏展开或收起时，页面不产生永久空白或底栏遮挡。

## 内容路由设计

### 现有行为

现有 `should_describe_keyframes(clean_text)` 只返回：

```json
{
  "need_visual": false,
  "reason": "普通口播"
}
```

它只决定是否下载视频、抽帧和调用视觉模型。无论返回值为何，路由最终都会调用 `extract_claims_from_video`，而该函数的提示词要求生成 3–5 条健康主张。

### 领域类别

内容路由器使用以下类别：

- `explicit_claim`：视频明确声称某种行为、食物、产品、治疗或指标会改善或损害健康。
- `implicit_guidance`：视频围绕减脂、增肌、睡眠、情绪管理等健康目标，展示观众可模仿的行为方案，即使没有直接说出确定因果结论。
- `health_context_only`：出现健身房、食物、药盒等健康元素，但没有明确主张、健康目标导向方案或可核验建议。
- `unrelated`：与健康信息核验无关。
- `pending_visual`：现有文字不足以判断，必须先查看画面或动作。

`explicit_claim` 和 `implicit_guidance` 继续分析；`health_context_only` 和 `unrelated` 停止；`pending_visual` 在关键帧解读后重新归类。

“减脂期我每天这样吃”属于 `implicit_guidance`，因为它包含明确健康目标、具体行为方案和可模仿性。主张提取阶段必须标记其为隐含建议，不得把模型推断伪装成视频原话。

### 路由器输入与输出

路由器输入包括媒体标题、可用描述、作者信息、清洗后的语音转写，以及在最终视觉判断阶段可用的关键帧描述。输出为严格 JSON：

```json
{
  "scope": "implicit_guidance",
  "decision": "continue",
  "need_visual": true,
  "reason": "围绕减脂展示可模仿饮食方案",
  "quotes": ["减脂期我每天这样吃"]
}
```

约束：

- `scope` 必须来自固定枚举。
- `decision` 只能为 `continue`、`stop` 或 `inspect_visual`。
- `quotes` 必须来自输入标题、转写或画面描述，不允许模型自行补写。
- 当输出无法解析、枚举非法或理由与决定冲突时，按路由失败处理，不进入主张提取。

### 两级流程

1. 获取媒体信息。
2. 用可靠元数据做高置信度预筛。预筛只能输出“明显无关”或“不确定”；不确定继续处理。
3. 完成语音转写。
4. 调用升级后的内容路由器，复用现有关键帧闸门的轻量模型调用。
5. 若决定停止，立即返回业务拒绝结果。
6. 若决定查看画面，执行现有抽帧与视觉解读，再用文字和画面完成最终归类。
7. 仅对最终决定为继续的视频调用主张提取。

第一级不能仅凭文件名、单个关键词或缺失的描述拒绝内容。本地上传通常缺少可靠元数据，应直接进入转写后的第二级判断。

“高置信度无关”必须同时满足：标题或上游结构化分类明确指向赛事直播/集锦、影视剪辑、游戏实况、旅游攻略或纯搞笑段子等非健康目的；并且标题与描述中不存在减脂、训练、饮食、睡眠、症状、疾病、治疗、用药等健康目标或健康主张线索。仅出现“足球”“美食”“旅行”等主题词不构成拒绝条件。预筛规则使用显式白名单式组合和自动化样例测试，不允许模型自由生成新的拒绝类别；不能满足全部条件时一律返回“不确定”。

## API 与前端状态

链接分析和本地上传采用相同的判别联合返回类型。

接受结果保持现有字段，并增加状态：

```json
{
  "status": "accepted",
  "scope": "explicit_claim",
  "reference": {},
  "claims": [],
  "keyframes": [],
  "topic": "健康说法核验"
}
```

业务拒绝使用正常 HTTP 成功响应，避免把预期的产品判断混同为服务故障：

```json
{
  "status": "rejected",
  "scope": "unrelated",
  "reason": "视频内容与健康信息核验无关",
  "matched_text": [],
  "reference": {}
}
```

前端新增联合类型并按 `status` 分支：

- `health_context_only`：中性提示“视频涉及健康场景，但没有识别到明确健康主张或可模仿方案。”
- `unrelated`：中性提示“这段视频不属于健康信息核验范围，FitProof 暂不进行分析。”
- 两种状态都返回输入页或展示输入页内的结果面板，并提供重新选择视频或粘贴其他链接。
- 不显示红色技术错误样式，不提供“仍然分析”。

## 异常处理

- 转写失败、文件损坏、上传超限、媒体获取失败和接口超时继续作为技术错误处理。
- 内容路由调用超时、返回非法 JSON 或违反枚举约束时，停止流程并提示“暂时无法判断视频是否属于核验范围，请重试”。
- 路由失败采用 fail-closed，不回退到强制生成主张。
- 关键帧解读失败时：若文字已足以归类为 `explicit_claim` 或 `implicit_guidance`，可继续文字分析；若路由状态仍为 `pending_visual`，停止并提示暂时无法判断。

## 代码边界

- 后端新增独立的路由结果模型、提示词构建、解析与标准化函数；接口路由只负责调度。
- 现有关键帧采样、视觉描述和主张提取保持各自职责，不把领域判断散落到多个提示词中。
- 前端 API 层负责解析判别联合；页面状态层负责 accepted/rejected 跳转；`InputPage` 只负责显示输入和中性拒绝提示。
- 移动端高度与安全区变量集中在全局样式或应用外壳中，组件不重复硬编码底栏高度。

## 测试计划

### 后端单元与接口测试

- 明确主张：“每天吃两个鸡蛋不会升高胆固醇” → `explicit_claim`、继续。
- 隐含指导：“减脂期我每天这样吃” → `implicit_guidance`、继续。
- 仅健康场景：“今天来健身房打卡” → `health_context_only`、停止。
- 完全无关：“今天这场足球比赛太精彩了” → `unrelated`、停止。
- 视觉待定：“大家看我这个动作” → `pending_visual` / 查看画面。
- 非法 JSON、非法枚举、模型异常 → 路由失败并停止。
- 链接与上传接口对拒绝内容返回同构业务结果。
- 对所有停止分支断言 `extract_claims_from_video` 未被调用。
- 对继续分支验证现有主张提取、关键帧和引用信息不回归。

### 前端与布局测试

- API 类型测试覆盖 accepted/rejected 联合。
- 页面状态测试覆盖两种中性拒绝提示、重新输入入口和技术错误样式。
- Playwright 使用 320×568、360×640、390×844、430×932 及横屏视口检查首屏与滚动行为。
- 自动断言 `document.documentElement.scrollWidth <= clientWidth`。
- 自动断言主分析按钮在 360×640 默认字体首屏内，且底部不被导航遮挡。
- 人工在至少一台 iOS Safari 和一台 Android Chrome 上检查动态地址栏、软键盘、字体放大和安全区。

## 完成标准

所有新增和既有相关测试通过；普通健康视频相对当前流程不增加独立的后置领域模型调用；被拒绝内容不会进入主张提取；指定移动视口满足布局验收行为；真实设备测试未发现底栏遮挡或横向溢出。
